# Terraform AWS Infrastructure — Plan

## Architecture

**Components.** One Terraform root module in `terraform/` and one shell wrapper in `scripts/`.
The module declares five groups of resources, each owning a file:

- *network* — a VPC, an internet gateway, two public subnets, a route table with its associations,
  and a security group admitting inbound HTTP/HTTPS to the load balancer.
- *data* — the DynamoDB table and the two SSM `SecureString` parameters holding RS256 key
  material.
- *compute* — the CloudWatch log group, the IAM execution role with its inline policy, and the
  Lambda function.
- *edge* — the ALB, the `lambda` target group with its health check, the listeners (shape decided
  by whether a certificate ARN was supplied), the `aws_lambda_permission`, and the target-group
  attachment.
- *interface* — variables, outputs, the example variables file, and the committed check fixture.

**Data flow at runtime.** A client reaches the ALB, whose listener forwards to the target group;
the target group invokes the Lambda through the Lambda API, not over the network, so the function
carries no VPC configuration. The function reads and writes DynamoDB and reads both SSM parameters
over public AWS endpoints. Structured logs land in the log group the stack created.

**Data flow at verification time.** `npm run infra:check` → `scripts/infra-check.sh` → a pinned
`hashicorp/terraform` container with the repository bind-mounted. The script writes a transient
`backend_override.tf` selecting the local backend, runs `fmt -check`, `init -backend=false`,
`validate`, and `plan -refresh=false` against `terraform/fixtures/check.tfvars`, then removes the
override on every exit path.

**Integration with what exists.** The stack consumes three contracts already fixed by shipped
features and invents none of them: the environment-variable schema in
`src/shared/config/environment.schema.ts` (FR14), the table shape in `scripts/create-table.ts`
(FR17), and the two SSM parameter names the key providers in `src/auth/infrastructure/keys/` read
(FR18/FR19). No file under `src/` is modified. The application is not aware the stack exists.

## Technical Decisions

- **Flat root module, files by concern; no child modules.** A module boundary costs a duplicated
  variables/outputs surface and buys reuse this feature has none of — one environment, one caller.
  Recorded in `brainstorm.md` with the two rejected alternatives.
- **Decomposition axis: horizontal, deliberately.** The work does not slice. `edge.tf` references
  the function declared in `compute.tf`, which references the table and parameters in `data.tf`,
  which reference `variables.tf`; `outputs.tf` reads from three of them. Every concern touches
  `variables.tf`, which is textbook shared-file gravity. Declaring fake disjoint slices here would
  produce clobbering under `dispatch-parallel` for no gain, so `Implementation Order` is a chain
  and the feature runs inline.
- **Replicating the existing script pattern rather than inventing one.** `scripts/infra-check.sh`
  follows `scripts/swagger-ui.sh` and `scripts/keel-watch.sh` — a bash script in `scripts/`,
  surfaced through an npm script, using Docker the way `docker-compose.yml` already does for
  DynamoDB Local. No new toolchain, no new language.
- **Terraform runs in a container, not on the host.** The version belongs to the repository. The
  container runs as the invoking uid/gid with a writable `HOME` and a mounted plugin cache, so it
  leaves no root-owned `.terraform/` in the tree and downloads the provider once (FR24, AC-16).
- **The check is not a pre-commit gate.** `terraform init` needs network access; wiring it into
  `.specify/gates/run-gates.sh` would make every commit in the repository — including commits that
  touch no infrastructure — depend on reaching `registry.terraform.io`. This is a knowing
  divergence from the project's "quality gates run before every commit" rule, and its cost is that
  a broken `.tf` can be committed. FR25 states it; `contract.md` covers the feature's own work.
- **Write-only SSM arguments over the placeholder pattern.** `value_wo`/`value_wo_version` keep the
  decrypted key out of state; `lifecycle { ignore_changes = [value] }` does not, because it
  suppresses the diff and not the refresh. This is what sets `required_version >= 1.11`.
- **`kms:Decrypt` on `"*"` with a `kms:ViaService` condition.** The scoped-looking alternative does
  not work: an alias in a policy `Resource` applies to the alias and not the key, and the real key
  ARN needs an account id and key id obtainable only through AWS-API data sources, which the
  credential-less plan forbids. The condition scopes the wildcard to SSM calls in the configured
  region. This is the one wildcard resource in the policy and AC-14 pins it as the only one.
- **Naming (from the `naming-conventions` lens).** Terraform identifiers are `snake_case`; every
  AWS resource name is `${var.project_name}-<role>`, one concept one name across the stack. The
  environment variables the function receives keep their `SCREAMING_SNAKE` wire names because
  `environment.schema.ts` owns that boundary — the stack does not rename anything the application
  already named.
- **Observability (from the `observability-and-instrumentation` lens).** The feature adds no
  instrumentation code; it decides where the existing `StructuredLogger` output lands and for how
  long. The log group is created by the stack rather than by the runtime so that its name,
  retention and permissions are declared, and the function depends on it so the runtime cannot win
  the race and create an unmanaged group first.
- **Lenses not applied.** `postgres-conventions` — no relational database. `typescript-conventions`
  — no TypeScript is added or changed.
- **`codebase-map` skipped, on purpose.** The map exists to keep `Architecture` and `File
  Structure` pointing at real paths in `src/`. This feature modifies nothing under `src/` or
  `test/`: it adds `terraform/`, one script, one ADR, and edits `package.json`, `.gitignore` and
  the README. Mapping the application tree would produce a document this plan never reads. The
  paths above were read directly instead.
- **The check takes an optional variables-file argument.** `scripts/infra-check.sh` defaults to
  the committed fixture but accepts a path as `$1`. Without it, AC-5 (a zone outside the region)
  and AC-7 (a supplied certificate) have no runnable command, since both prove behavior that only
  appears under different variable values. Found by `analyze` before implementation started.

## Data Layer Contract

The stack declares a table but introduces no schema. The single-table design, its key grammar and
its item mapping are owned by `src/shared/persistence/` and were set by feature 001; this plan
reproduces the same shape in Terraform so the table can be created by the stack instead of by
`scripts/create-table.ts`.

- **Code↔schema mapping**: unchanged, and not this feature's concern. The mapping site remains
  `src/shared/persistence/`; no code reads a name this plan introduces.
- **Tables/columns**: one table. String partition key and string sort key, matching
  `scripts/create-table.ts` exactly. `PAY_PER_REQUEST` billing. TTL enabled on the `ttl` attribute.
  Point-in-time recovery enabled. No secondary index — the catalog query uses the base table.
- **Indexes**: none. Adding one would require a matching `index/*` ARN in the execution policy;
  FR19's action list deliberately has none.
- **RLS**: N/A — DynamoDB has no row-level security, and the product is explicitly not
  multi-tenant. Access is decided at the API boundary by the JWT guard, not per row.
- **Migration**: N/A — no migration. The table is created, not altered. Deletion protection and
  `prevent_destroy` are deliberately absent (FR17) because the runbook ends with a teardown; the
  accepted consequence is that a teardown deletes all data.

## Implementation Order

Serialized, for the reason recorded above. Each step ends with `npm run infra:check` green, so a
regression is attributed to the step that caused it.

1. `.gitignore` entries, then `terraform/versions.tf`, `providers.tf`, a minimal `variables.tf`,
   and `terraform/fixtures/check.tfvars`. A configuration with no resources yet.
2. `scripts/infra-check.sh` and the `infra:check` npm script, including the transient backend
   override with cleanup on every exit path. From here on the harness proves each later step.
   Covers AC-1, AC-2, AC-16.
3. `network.tf`, plus the availability-zone `validation` block. Covers AC-4, AC-5.
4. `data.tf` — table and both SSM parameters. Covers AC-12, AC-13.
5. `compute.tf` — log group, execution role and inline policy, function. Covers AC-10, AC-11,
   AC-14, AC-15.
6. `edge.tf` — load balancer, target group with its health check, the conditional listeners, the
   Lambda permission, the attachment. Covers AC-6, AC-7, AC-8, AC-9.
7. `outputs.tf` and `terraform.tfvars.example`; commit `.terraform.lock.hcl`. Covers AC-3.
8. `docs/architecture/adr/0008-alb-lambda-transport.md`. Covers AC-17.
9. The README runbook. Covers AC-18.
10. Full `npm run infra:check` plus `.specify/gates/run-gates.sh`, then the plan read end to end
    and each verdict stamped into `contract.md`.

## How to Validate

**There is no application code in this feature, and that changes what testing means here.** The
project requires a failing test before production code; this feature produces no functions, no
branches and no runtime behavior to assert on, so a unit test would have nothing to observe. The
honest analog, and the rhythm each step above follows, is: run `npm run infra:check` before adding
a resource and see it absent from the plan, add the declaration, run it again and see it appear
correctly. That is red-green applied to a declarative artifact, and it is stated plainly rather
than dressed up as TDD.

- **Unit tests**: none. Nothing executable is added. `npm run test:unit` must still pass unchanged,
  as evidence the feature touched no application code.
- **Integration and e2e tests**: none added, and all three existing suites must still pass
  unchanged for the same reason.
- **The feature's own verification**: `npm run infra:check` for AC-1, AC-2 and AC-16, and a read of
  the plan it produces for AC-3 through AC-15, with each verdict recorded in `contract.md`. AC-17
  and AC-18 are document checks. The per-`AC-N` command and observable belong in `contract.md`, not
  here.
- **Quality checklist**: `.specify/gates/run-gates.sh` green; every Terraform file under 400 lines;
  no `.terraform/`, state file, or root-owned artifact left in the tree after a check; no secret
  value anywhere in the repository or in a plan's output.
